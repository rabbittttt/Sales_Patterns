## 二、发现的问题

### P1-1 遗留 Excel 生成链路：与"不生成 Excel 报告"规范冲突的死代码

**位置**：`core/export_excel_openpyxl.py:239`（`ExcelBuilder`）、`:345`（`_atomic_save`）、`:374`（`export_workbook`）、`:725-732`（独立 CLI 入口）；`tests/test_export_excel.py`（216 行）。

**现状**：AGENTS.md 与 README:224 均明确"当前版本只输出网页，不再生成 Excel"。生产管线（`core/export_html.py`）只复用该模块的 5 个纯函数：`_choose_grouping`、`_selected_metrics`、`_report_series`、`build_monthly_profiles`、`_headline_findings`。而完整的 Excel 写出能力——17 张工作表的 `ExcelBuilder`、原子保存校验、以及 `python core/export_excel_openpyxl.py evidence.json out.xlsx` 的独立命令行入口——仍然存在且可运行，仅被 `tests/test_export_excel.py` 测试引用。

**影响**：
- 约 490 行死代码 + 216 行测试持续消耗维护成本（每次口径调整都要同步维护两套渲染）；
- 独立 CLI 仍可产出 `.xlsx`，与规范矛盾的能力保留了一个可执行出口；
- 文案上残留旧口径，如 `export_workbook` 中的"净大定（留存大定）"标题（`:400`、`:409`、`:433`、`:682`）——现行 UI 统一称"留存大定"。

**建议**：把 `_choose_grouping`/`_selected_metrics`/`_report_series`/`build_monthly_profiles`/`_headline_findings` 迁入独立模块（如 `core/report_grouping.py`），删除 `ExcelBuilder`、`export_workbook`、`_atomic_save` 与 `__main__` CLI，删除 `tests/test_export_excel.py` 中针对 Excel 写出的用例（保留辅助函数用例），并同步清理 README 中 Excel 相关章节。

### P1-2 节假日日历双源不一致：2021 硬编码与 2024 补丁未回流 `china_calendar.py`

**位置**：`static/analyze_sales_patterns.py:42-55`（`load_calendar`）vs `core/china_calendar.py:17-69`。

**事实**：
1. `load_calendar()` 在运行时给 `periods[2024]` 打补丁：元旦起点改为 `2023-12-30`、端午节改为 `2024-06-08`（即国务院公布的完整连休区间，与该模块文件头"记录完整放假区间"的注释约定一致）。但 `china_calendar.py` 本体的 2024 数据仍是 `2024-01-01` 与 `2024-06-10`（`china_calendar.py:36,40`）——**同一份事实有两个版本，修正写在错误的层**。
2. 2021 年的节假日、调休上班日与来源 URL 只硬编码在 `static/analyze_sales_patterns.py:46-48`，`china_calendar.py` 完全没有 2021（`SOURCE_URLS` 从 2022 起）。
3. `china_calendar.py` 自带的 `classify_day`（`:103`）、`window_profile`（`:118`）、`calendar_payload`（`:139`）及由未打补丁数据生成的 `HOLIDAY_DATES`（`:93`）在全项目**没有任何调用方**（已用 grep 全量确认）。它们一旦被未来代码使用，分类结果会与主分析的日历不一致（例如 2023-12-30 在主分析中是元旦假期，在 `classify_day` 中是普通周末）。

**影响**：现在不影响输出（两个入口都经 `load_calendar`），但属于典型的"埋雷分叉"：任何人基于 `china_calendar` 的公开函数做扩展（README 也把 `china_calendar.py` 列为共用模块）就会得到另一套日历。

**建议**：将 2021 数据与 2024 元旦/端午修正直接写入 `china_calendar.py` 的数据表；删除 `load_calendar()` 中的补丁；删除或明确启用 `classify_day`/`window_profile`/`calendar_payload` 三个无调用方的函数。

### P2-1 未文档化的 `PLANHUB_DATA_ROOT` 环境变量耦合

**位置**：`core/data_paths.py:17`。

`shared_data_root()` 的优先级实际是 `SHARED_DATA_ROOT` > `PLANHUB_DATA_ROOT` > 默认 `../工作台数据`，但 AGENTS.md 和 README 只写了 `SHARED_DATA_ROOT`。`PLANHUB_DATA_ROOT` 是跨项目的约定：若其他项目在全局（如用户级环境变量）设置过它，本项目的输入路径会被**静默改向**。虽然路径缺失会明确报错（符合"不回退旧副本"），但报错信息只会指向一个用户意想不到的目录。

**建议**：在 AGENTS.md 与 README 的路径章节补写 `PLANHUB_DATA_ROOT` 的行为与优先级；若该约定已废弃则移除。

### P2-2 同名表头静默覆盖：同一项目存在两种策略

**位置**：`static/analyze_sales_patterns.py:68-72`（`_workbook_records` 用 `dict(zip(header, values))`）。

逐日表/车型信息/说明表读取时，若源表存在重复列名，后者会静默覆盖前者。而 `core/source_patterns.py:171-179`（`_headers_and_rows`）对同名列做了 `列名__2` 去重。两套读取器策略不一致，逐日表（最核心的数据）反而是无防护的一侧。

**建议**：`_workbook_records` 对齐 `source_patterns` 的去重策略，或至少在发现重复表头时计入 audit 计数。

### P2-3 动态服务无构建超时

**位置**：`dynamic/serve_sales_patterns.py:235-264`（`_building_tick`）。

生成子进程每秒轮询退出状态，但没有最长构建时限。若子进程因异常场景挂死（如 openpyxl 遇到特殊文件陷入死循环、磁盘满重试等），服务会无限期停留在 `building` 状态，不再产生新结果也不会报错。当前实现依赖子进程自身"分析期间源文件变化即中止"的防御（`static/analyze_sales_patterns.py:990-991`），正常路径可靠，但缺少兜底。

**建议**：为构建增加可配置的最大时长（如 `--build-timeout`，默认 30 分钟），超时终止子进程、保留上次报告并转为重试。

### P2-4 旧版报告被静默丢弃，页面无解释

**位置**：`dynamic/serve_sales_patterns.py:147-155`。

启动时若已有报告不符合新版结构（缺少唯一 `patterns-data` 脚本或有效 SHA-256，例如旧版本生成的文件），只会记一条控制台日志"已有报告无法加载"，页面回退到"正在更新…"占位直到首次构建成功。对只在浏览器前等待的用户没有任何提示原因。

**建议**：在占位页中附带"上次报告无法识别，已等待重新生成"的说明（内容不受信任，注意仅输出静态文案，不要回显异常细节）。

## 四、安全与数据合规审查

**结论：整体姿态良好，未发现高风险项。**

- **服务暴露面**：仅绑定 `127.0.0.1`，`SO_EXCLUSIVEADDRUSE` 防端口劫持；只响应 `/`、`/index.html`、报告文件名与 `/api/status` 四类路径，无任意文件读取；状态接口只暴露哈希与 ID，不泄露路径。
- **回环检测防代理劫持**：`existing_instance` 用 `ProxyHandler({})` 绕过企业代理查询 loopback（`serve_sales_patterns.py:387`），注释明确。
- **注入防护**：网页数据 JSON 序列化后统一转义 `& < >` 与 U+2028/2029（`export_html.py:177-178`），模板占位符用 `re.sub` + 回调替换避免反向引用歧义；前端全部走 `textContent`/`createElement`，无 `innerHTML`；CSV 导出对 `=+-@` 开头的字符串加前缀防公式注入（`patterns.js:1468`）。
- **输入完整性**：静态入口生成前后两次 SHA-256 比对；动态服务发布前以"报告内嵌 SHA-256 == 当前稳定输入摘要"双重校验，且构建期间持续探测输入变化，任一不符即丢弃本次结果保留旧版——数据一致性设计值得肯定。
- **供应链**：生产依赖仅 `openpyxl>=3.1,<4`；Node/Playwright 明确标注为开发依赖。
- **隐私**：生成的 HTML 内嵌业务数据，README 已提示"迁移和分享范围按源文件相同要求处理"；仓库本身不含任何业务数据。
